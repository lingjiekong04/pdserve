# 简历与面试展示

## 可直接采用的简历条目

**PDServe：混合长短请求的 Prefill/Decode 分离推理服务**

- 基于 Qwen2.5-7B-Instruct（BF16，16K context）、SGLang 与 Mooncake，在2×A100 80GB上打通独立P/D、KV传输与SSE响应；复用上游执行和通信能力。
- 实现token/KV/slot准入、128有界队列、30s排队超时和短长请求3:1+5s aging调度；通过专项真卡排队验收证明调度顺序和背压行为。
- 增加原生阶段事件和cleanup ACK，覆盖各阶段取消、传输超时、节点退出、隔离与成对恢复；区分响应终态、预算释放和实际引擎清理。
- 构建3种拓扑、36次运行、1440个请求的同卡对照及真实TTFT/ITL测量；发现P/D未普遍超过双副本，并识别长请求配置的KV等待/传输窗口退化及实验混杂。

## 数字如何解释

80%短请求/2req/s的历史记录中，pd_fair相对pd_fifo总体TTFT p95为752.86ms对2297.31ms，观测上约低67.2%；完成吞吐1.9695对1.8362req/s，约高7.3%。但36次性能运行没有网关重排，所以不能写“公平算法优化使TTFT降低67%”。可以在面试中将其作为观测结果与因果审查的案例。

同时保留：该场景pd_fair仍比双副本吞吐低约3.6%；长请求占80%的高到达率配置退化更明显。真实负结果和证据边界比选择性提升数字更能说明系统理解。

## 60秒介绍

我做的是SGLang上的P/D服务层：精确token准入、KV与slot预算、有界队列、公平调度以及取消和故障生命周期。我通过引擎补丁把response终态与真实资源清理分开，只有匹配的cleanup ACK才释放网关预算。最后在两张A100上比较了双混合副本、P/D FIFO和P/D公平配置，共36次运行。实验没有证明PD天然更快，也没有充分触发性能负载下的网关重排；专项排队测试证明了调度功能。这个项目让我识别了下游KV等待、观测开销和实验因果归属的问题。
